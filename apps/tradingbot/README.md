# Демо-бот на фьючерсах Bybit: четыре торговые системы

Бот берёт **настоящие** данные с Bybit (фьючерсы USDT-перпетуалы), сам ищет монеты
под торговую стратегию и в момент точки входа **записывает** фейковую сделку:
«вот здесь я бы зашёл, вот здесь бы вышел». Реальные ордера не отправляются
никуда и API-ключи не нужны — используется только публичный рынок.

Торговых систем четыре, и запускаются они по одной на процесс — так журнал
сделок каждой остаётся отдельным, а результаты можно честно сравнивать.
Размер сделки у всех общий: **20 $ маржи с плечом x20 = 400 $ позиции**
(`RiskConfig`).

| Ключ | ТС | Суть | Код |
|------|----|------|-----|
| `--strategy impulse` (по умолчанию) | шорт истощения импульса | монета резко выросла, рост выдохся — шортим откат | `bot/strategy.py`, `bot/engine.py` |
| `--strategy density` | плотности в стакане | стоит крупная неспуферская заявка — встаём лимиткой перед ней | `bot/density.py` |
| `--strategy breakout` | импульсный пробой уровня | у явного уровня кипит торговля — лонг, выход когда активность упала | `bot/breakout.py`, `bot/activity.py` |
| `--strategy btc` | биткоин | BTC просел на пару процентов к опоре — лонг с целью +5 $ | `bot/btc.py` |

В кластере это просто четыре пода со своими томами, а панель `/tb` переключается
между ними вкладками (см. [setupToServer.md](setupToServer.md), раздел 9).

## Установка

```powershell
pip install -r requirements.txt
```

Нужен Python 3.10+.

## Запуск

```powershell
python run.py            # демо-торговля в реальном времени
python run.py --web      # то же + веб-панель на http://localhost:8080
python run.py report     # сводка по журналу сделок
python run.py selftest   # проверка логики на синтетических свечах, без сети
```

Полезные ключи:

```powershell
python run.py --margin 20 --leverage 20 --stop 5 --take 15
python run.py --min-change 0.15 --max-positions 5
python run.py --no-orderbook --debug
python run.py --strategy breakout --version 0.1   # конкретная ТС и версия
```

Остановка — `Ctrl+C`, бот напечатает итог сессии.

## Версии торговых систем

У каждой ТС есть версии (`v0.1`, `v0.2`, …). Смысл в том, что **новая версия не
заменяет старую**: обе торгуют одновременно, каждая ведёт свой журнал, и через
неделю видно, какая лучше. Сравнивать иначе бессмысленно — рынок у них должен
быть один и тот же.

```powershell
python run.py --versions                              # список версий всех ТС
python run.py --web --strategy breakout --version 0.1 # запустить конкретную
python run.py --web --strategy breakout               # без ключа — последняя
```

Что есть сейчас:

| ТС | Версии |
|----|--------|
| `impulse` | `0.1` |
| `density` | `0.1`, `0.2` |
| `breakout` | `0.1`, `0.2` |
| `btc` | `0.1` |

Реестр — в `bot/versions.py`. Версия это именованный набор отличий от базового
конфига:

```python
VERSIONS["breakout"]["0.2"] = Version(
    notes="порог активности ниже, входим чаще",
    overrides={"breakout": {"min_entry_score": 0.35}},
)
```

`overrides` — это `{секция конфига: {поле: значение}}`; пустая секция `""`
означает корень `Config`. Имена полей проверяются при старте: опечатка валит
бота с внятной ошибкой, а не оставляет версию торговать ровно как предыдущая.

Если версия меняет не числа, а саму логику — положите её код рядом
(`bot/breakout_v2.py`) и укажите `engine="bot.breakout_v2:BreakoutEngine"`.
Старая версия продолжит работать на прежнем коде.

### Как выкатить новую версию

Четыре места, старую при этом не трогаем:

1. `bot/versions.py` — описать версию;
2. `infrastructure/k8s/base/tradingbot-chart/values.yaml` — **добавить** элемент
   в `bots[]` (появятся Deployment, Service и отдельный PVC);
3. `apps/client/nginx.conf` — роут `/tb/api/<тс>-v<версия>/`;
4. `apps/client/html/tb.html` — элемент в `versions` нужной ТС.

В именах ресурсов и URL точка запрещена, поэтому версия пишется как `v0-1`:
`tradingbot-breakout-v0-1`, `/tb/api/breakout-v0-1/`, ссылка `/tb#breakout-v0-1`.

На панели версии переключаются чипами в карточке ТС; итог каждой виден сразу,
без переключения. Старую версию удаляют, когда сравнение закончено, — вместе с
её PVC (у него `resource-policy: keep`, сам ArgoCD его не тронет).

## Торговая система №1: шорт истощения импульса

**1. Отбор монет** (`bot/scanner.py`)
- USDT-перпетуалы, рост за 24ч > 10% (и < 300%, чтобы не лезть в пустые пампы);
- альткоин: BTC, ETH, стейблы и плечевые токены исключены;
- средние объёмы: оборот 3M–250M $ за сутки;
- рост именно резкий: ≥45% дневного движения сделано за последние 4 часа;
- листингу больше 7 дней.

**2. Импульс** (`bot/strategy.py: find_impulse`) — на 1m, 5m и 15m ищется окно из
4–12 свечей, где:
- суммарный рост выше порога ТФ (1m: 2%, 5m: 3.5%, 15m: 5.5%);
- откаты внутри импульса ≤ 35% от всего движения, красных свечей ≤ 1/3,
  ни одна свеча не проваливается ниже начала импульса — то есть рост «без просадок»;
- объём в импульсе ≥ 1.4× фонового.

Нужно подтверждение минимум на 2 таймфреймах из 3.

**3. Точка входа — «затуп»** (`find_stall`). Импульс должен начать тухнуть; проверяются
5 признаков, требуется минимум 3:
- свечи сузились (диапазон < 60% среднего по импульсу);
- объём упал (< 75% пика импульса);
- появились верхние тени (≥ 35% диапазона свечи);
- последние свечи не обновляют хай импульса;
- скорость роста упала более чем вдвое от пиковой.

Если цена уже упала от вершины больше 2% — вход отменяется, поезд ушёл.

**4. Сделка** (`bot/paper.py`) — шорт на **20 $ маржи с плечом x20** = позиция 400 $.
- стоп-лосс — цена, на которой чистый убыток равен **5 $** (≈ +1.2% против нас);
- тейк-профит — **+15 $** (≈ −3.8% по цене);
- комиссия тейкера 0.055% в обе стороны заложена в уровни, чтобы −5$ и +15$ были
  именно чистыми;
- безубыток: после +6 $ стоп подтягивается к цене входа.

**Выход «прогноз не сбылся»**: если цена сходила вниз, но вернула ≥55% достигнутого
хода — закрываемся, не дожидаясь стопа. Терпение зависит от ведущего таймфрейма —
чем он старше, тем на более долгое падение мы рассчитываем:

| ТФ | ждём реакции | максимум в позиции |
|----|--------------|--------------------|
| 1m | 4 мин | 12 мин |
| 5m | 15 мин | 45 мин |
| 15m | 45 мин | 150 мин |

**5. Стакан** (`bot/orderbook.py`). Бот опрашивает стакан раз в секунду и ведёт историю
по каждому ценовому уровню, чтобы отличить настоящую плотность от спуфера:

- плотность = уровень, чей объём в 6+ раз больше медианного в зоне ±1.5% от цены;
- **настоящей** она считается, только если прожила ≥6 опросов подряд и не усохла
  более чем на 45% от своего максимума;
- если крупная заявка исчезла рано или испарилась при подходе цены — это спуфер,
  он не влияет на решения и попадает в счётчик `spoof`.

Реакция бота:
- настоящая **ask**-стена сверху = сопротивление → плюс к скору шорта;
- настоящая **bid**-стена ближе 0.6% под ценой → **вход запрещён**;
- bid-стена дальше → минус к скору;
- перекос стакана в сторону покупателей > 1.8× → вход запрещён;
- если в открытой позиции под ценой встала настоящая bid-стена, а мы в плюсе —
  фиксируем прибыль, не дожидаясь тейка.

Итоговый скор сетапа = 0.45×импульс + 0.25×подтверждения ТФ + 0.30×затуп ± стакан.
Порог входа — 0.55 (`entry.min_setup_score`).

## Торговая система №2: плотности в стакане

`python run.py --web --strategy density`, код в `bot/density.py`,
параметры в `bot/config.py: DensityConfig`.

Идея: крупная лимитная заявка (плотность) держит цену — чтобы пройти уровень,
рынку надо выкупить или продать весь её объём. Пока стена стоит, от неё
отскакивают. Значит, встаём лимиткой **перед** стеной и выходим, как только
опора исчезла.

**1. Отбор монет** — не по росту, а по активности: монета должна быть живой и
подвижной, потому что в тонком стакане «мусорной» монеты плотность пробивают
первым же рыночным ордером.
- оборот за сутки 20M–3000M $;
- ATR по 5-минуткам ≥ 0.30% от цены — монета реально ходит;
- спред ≤ 0.10% (проверяется уже по стакану, в момент поиска сетапа);
- стейблы и завёрнутые токены исключены.

**2. Поиск плотности** (`find_wall_setup`) — уровень считается плотностью, если он:
- крупнее медианного уровня зоны в 8 раз **и** не меньше 40 000 $;
- не дальше 0.5% от текущей цены;
- **не спуферский**: прожил ≥ 10 опросов стакана подряд и не усох больше чем на
  30%. Этим занимается тот же `BookTracker`, что и у первой ТС: он ведёт историю
  по каждому ценовому уровню и ловит заявки, которые снимают при подходе цены;
- доминирует над встречной стороной зоны минимум вдвое — то есть дисбаланс
  действительно очевиден, а не «с обеих сторон примерно поровну».

**3. Вход** — лимитка на 0.04% перед стеной (не в саму стену: на её цене мы будем
последними в очереди). У bid-стены это покупка, у ask-стены — продажа.
Лимитка снимается, если плотность исчезла раньше исполнения или прошло 3 минуты.
Исполнение считается по стакану, комиссия — мейкерская.

**4. Выход** — по судьбе самой плотности, а не по времени:
- плотность **съедена на 80%** от своего максимального размера — выходим;
- плотность **снята** из стакана — выходим;
- **тейк +5 $** чистыми;
- предохранители: стоп за уровнем (или по деньгам — берётся тот, что ближе) и
  40 минут максимума на сделку.

Стоп и лимит по времени спецификацией ТС не заданы — они добавлены как
страховка: без них сделка, где цену увели сквозь уровень, висела бы вечно.
Оба параметра в `DensityConfig` (`stop_loss_usd`, `stop_beyond_wall_pct`,
`max_hold_minutes`); чтобы выходить строго по плотности, поставь их пошире.

### Версия 0.2: то же самое, но в обратную сторону

`--strategy density --version 0.2`, код в `bot/density_v2.py`. Версия 0.1
продолжает работать рядом.

Всё идентично 0.1 — отбор монет, поиск стены, все фильтры, цена срабатывания
ордера, расстояния целей, правила выхода, — кроме направления сделки:

| | 0.1 | 0.2 |
|--|-----|-----|
| bid-стена (плотность на покупку) | ЛОНГ | ШОРТ |
| ask-стена (плотность на продажу) | ШОРТ | ЛОНГ |

Смысл: 0.1 ставит на то, что плотность **удержит** цену (отскок от стены),
0.2 — на то, что её **пробьют**. Обе версии видят одни и те же стены в одни и
те же секунды, поэтому разница в результате — это разница направления, а не
удачи с отбором монет.

**Два отличия сверх стороны**, без которых версия была бы не зеркальной, а
сломанной:

1. **Тип ордера.** В 0.1 сторона следует из геометрии: bid-стена лежит *ниже*
   цены, и перед ней можно поставить только лимитку на покупку; ask-стена
   *выше* — только на продажу. При простой инверсии получилась бы продажа по
   цене ниже рынка — такой ордер исполнился бы мгновенно по текущей цене, а не
   дождался подхода к стене. Поэтому в 0.2 ордер стоповый: срабатывает по той
   же цене и по тому же событию, но открывает противоположную позицию.
2. **Комиссия входа тейкерская** (0.055% вместо мейкерских 0.02%): стоповый
   ордер исполняется по рынку. Оставить мейкерскую значило бы приукрасить
   статистику 0.2 и сделать сравнение версий нечестным.

Из-за второго пункта расстояние до тейка в *цене* у версий отличается на ~2.6%
— цене надо пройти чуть дальше ради тех же чистых +5 $. В деньгах цели
одинаковые.

Выходы не менялись сознательно: «плотность съедена на 80%» и «плотность снята»
закрывают сделку в обеих версиях. Учтите, что для 0.2 съедание стены — это
как раз развитие её собственной идеи (пробой), но правило оставлено общим,
как вы и просили. Если захотите, чтобы 0.2 держала сделку при съедании стены —
это будет уже версия 0.3.

## Торговая система №3: импульсный пробой уровня

`python run.py --web --strategy breakout`, код в `bot/breakout.py` и
`bot/activity.py`, параметры в `bot/config.py: BreakoutConfig`. **Только лонги.**

Ключевая мысль: **пробой торгуется по активности, а не по цене.** Само по себе
пересечение уровня не значит ничего — цена может переползти его на трёх сделках
и сползти обратно. Дальше её толкает торговля у уровня: летит лента принтов,
ставятся и снимаются заявки, цена дёргается туда-сюда. Эта же активность первой
и заканчивается, когда импульс выдохся, — раньше, чем развернётся котировка.

**1. Монета в восходящем тренде.** Три условия сразу, иначе под «рост за сутки»
попадает отскок внутри падения: цена выше быстрой SMA(20), быстрая выше
медленной SMA(50), и сама медленная выросла минимум на 0.5% за 20 свечей.

**2. Уровень должен быть явным** (`bot/levels.py`):
- **2+ касаний**, и они разнесены во времени — три свечи подряд у одной цены
  это одно событие, а не три подтверждения;
- **после касания цена реально отбивалась** вниз хотя бы на 0.6%. Без этой
  проверки в «уровни» попадает любой локальный максимум, на который рынок никак
  не отреагировал. Отбой считается по медиане касаний, а не по рекордному.

**3. Вход — по активности у уровня** (`bot/activity.py`). Цена должна быть в
зоне уровня ±0.4%, а **где именно — под уровнем или уже над ним, неважно**:
входить можно и до пробоя. Что меряется в окне 60 секунд:

| Метрика | Что показывает | Порог |
|---------|----------------|-------|
| `trades_per_min` | темп ленты принтов | ≥ 60 |
| `volume_per_min` | оборот деньгами (отсекает «активность» из мелочи) | ≥ 10 000 $ |
| `near_share` | доля оборота, прошедшая **в зоне уровня** | ≥ 25% |
| `book_notional` | сколько денег стоит заявками в зоне | ≥ 50 000 $ |
| `swings` | сколько раз цена сходила через уровень | ≥ 1 |
| `buy_ratio` | кто агрессор — берут по рынку вверх | ≥ 50% |

Из них собирается сводный `score` (0…1), и вход требует **двух** условий сразу:
`score ≥ 0.45` **и** превышение фона самой монеты в 1.6 раза. Одного
абсолютного порога мало: у тухлой монеты 30 принтов в минуту — это много, у
ликвидной — мёртвая тишина, поэтому фон считается по медиане последних
40 замеров этой же монеты.

**4. Выход — как только активность упала.** Это главное правило, и цена в нём
не участвует вовсе: выходим и в плюс, и в минус.
- активность упала до **55% от своего пика** за время сделки (пик считается от
  максимума, а не от входа: импульс часто разгоняется уже после открытия);
- либо просела ниже абсолютного пола `min_hold_score`;
- предохранители: тейк +8 $, денежный стоп −5 $, уход цены под уровень на 0.4%,
  «импульс не начался за 15 минут», потолок удержания 90 минут.

**Про лимиты API.** Замер активности дорогой — на каждый уходит запрос ленты и
запрос стакана, поэтому циклы разнесены: список монет обновляется раз в 4
минуты, уровни и «кто у уровня» — раз в 45 секунд, и только по горячим монетам
идёт замер активности раз в 3 секунды.

**Пороги откалиброваны по живому рынку** (08.09.2026): у активной монеты
получается 700–800 принтов/мин при обороте ~58 тыс. $/мин и `score` 0.58,
у вялой — 30 принтов/мин и `score` 0.15. Первые прикидки были мимо: порог
оборота в 30 тыс. $ не проходил никто, а порог заявок в 15 тыс. $ проходили все.
Если бот входит слишком редко или слишком часто, крутить надо именно эти числа
в `BreakoutConfig`.

### Версия 0.2: уровень строго НА ПРОБОЙ

`--strategy breakout --version 0.2`, код в `bot/breakout_v2.py`, параметры в
`bot/config.py: BreakoutV2Config`. Версия 0.1 продолжает работать рядом.

Появилась после жалобы (08.09.2026): *«открыл сделку, хотя по той монете не
было уровня на пробой, и тренд не особо восходящий»*. Разбор подтвердил:

- **уровень мог быть позади цены.** `pick_level` в 0.1 брала ближайший уровень
  **по модулю** расстояния, поэтому годился и уровень *ниже* цены — давно
  пробитый. Замер на живом рынке: из четырёх уровней, найденных 0.1, все
  четыре лежали ниже цены (−0.48%, −0.77%, −0.98% и один прямо на ней);
- **зона входа была симметричной** (±0.4%) — вход разрешался и когда цена уже
  ушла выше уровня;
- **тренд проверялся мягко**: рост от 3% за сутки, наклон средней от 0.5%.

Что изменено в 0.2:

| | 0.1 | 0.2 |
|--|-----|-----|
| Сторона уровня | любая | только впереди: цена идёт к нему снизу |
| Зона входа | ±0.4% симметрично | 0.6% снизу, 0.15% сверху |
| Проверка «уровень не пройден» | нет | цена под уровнем в ≥75% последних 20 свечей |
| Горизонт истории | 120 свечей (30 ч) | 400 свечей (100 ч) |
| Касаний | 2 | 3 |
| Отбой от уровня | 0.6% | 0.8% |
| Рост за сутки | ≥3% | ≥4% |
| Наклон средней | ≥0.5% | ≥0.8% + держится ≥60% свечей |
| Активность | только у уровня | плюс порог по самой монете |

**Про горизонт истории.** Это оказалось важнее прочего: за 30 часов монета в
восходящем тренде успевает уйти выше всех своих сопротивлений, и впереди не
остаётся ни одного уровня. Замер: при 120 свечах уровней впереди 0 у 10 монет,
при 400 — 5 уровней у 4 монет.

**Тренд и уровень конфликтуют по своей природе**: чем сильнее разгон, тем выше
цена относительно своих сопротивлений. Поэтому пороги тренда в 0.2 строже 0.1,
но не запредельны — при 6%/1.5% проходили 3 монеты из 10 и ни у одной не было
уровня впереди; при 4%/0.8% проходят 6, и кандидаты появляются.

**Ожидайте редких сделок.** Совпадение «восходящий тренд + явный уровень с 3
касаниями впереди + цена подошла к нему + всплеск активности» случается нечасто
— это цена избирательности. Если сделок совсем нет, смягчать надо в первую
очередь `min_entry_score` и `min_activity_ratio`, затем пороги тренда.

## Торговая система №4: биткоин

`python run.py --web --strategy btc`, код в `bot/btc.py`,
параметры в `bot/config.py: BtcConfig`. **Только лонги, только BTCUSDT.**

BTC регулярно даёт короткие проливы, после которых цена возвращается. Покупаем
такой пролив: **тейк +5 $, стоп −2 $**.

- **Вход**: просадка 2–8% от максимума за последние 4 часа (по 5-минуткам).
  Глубже — это уже не откат, а слом, лонгом такое не ловим.
- **Опора обязательна**: под ценой должна быть либо горизонтальная поддержка с
  касаниями (не дальше 0.6%), либо настоящая плотность на покупку в стакане
  (не дальше 0.4%). Без опоры бот просто ждёт — пропущенный вход стоит ноль,
  а пойманный нож стоит денег. Отключается флагом `require_support`.
- Потолок удержания — 2 часа, кулдаун между сделками — 10 минут (монета одна,
  общий получасовой простой оставил бы бота почти без сделок).

Бот подолгу бывает без сделок: просадка на 2% за 4 часа случается не каждый
день. Это нормально; частота регулируется `min_dip_pct` и `dip_window_candles`.

## Настройка

Всё в `bot/config.py`, по разделам: `ScreenerConfig`, `ImpulseConfig`, `EntryConfig`,
`RiskConfig`, `ExitConfig`, `OrderbookConfig` (ТС импульса), `DensityConfig`,
`BreakoutConfig` и `BtcConfig`. Логика стратегий в код не зашита числами —
меняй конфиг.

## Веб-панель и сервер

`python run.py --web` поднимает страницу с журналом торговли на `:8080`
(таблица сделок, открытые позиции, статистика, хвост лога, скачивание CSV).
Данные она берёт из тех же файлов в `data/`, отдельная база не нужна.

Развёртывание в Docker/Kubernetes и описание всех эндпоинтов — в
[setupToServer.md](setupToServer.md). Готовые `Dockerfile`, `docker-compose.yml`
и `k8s/tradingbot.yaml` лежат в корне проекта.

## Важно

Это симулятор на реальных котировках, а не гарантия результата. Демо-исполнение
считает вход и выход по последней цене без проскальзывания и без учёта того, что
на тонком альткоине позицию в 400 $ рынок двинет. На реальных деньгах результат
будет хуже — сначала набери статистику в `trades.csv`.
